# Архітектура Sonoff Controller

Статус: початкова реалізація. Правила бойлера погоджені: OFF одразу, ON після 20 хвилин стабільної мережі. GPIO та видача сертифіката потребують реального середовища. Live eWeLink протестовано на дозволеній Skvyra (10025391ef): OFF → ON → відновлення OFF. Токени імпортуються з ../tokens.json і не комітяться.

## Платформа

Raspberry Pi Zero 2 W має 512 МБ RAM. Пропозиція: Raspberry Pi OS Lite 64-bit, Python 3.12, FastAPI/Uvicorn, HTTPX, SQLite, Jinja2 та невеликий JavaScript без Node.js у runtime. Один процес і один worker обслуговують вебзапити та фонові завдання. Go для цього навантаження не потрібен.

```text
Ізольований аналізатор → GPIO/АЦП → debounce → автоматизація розеток
                                                   ↓
Браузер ← FastAPI ← стан / журнал SQLite ← клієнт eWeLink → Sonoff
```

## Датчик і попередні піни

Для визначення наявності мережі достатньо ізольованого цифрового сигналу. Raspberry Pi не має аналогових входів. Нульовий споживаний струм не доводить відсутності напруги мережі.

**Лише для підтвердженого сухого контакту:** GPIO17 (BCM, фізичний пін 11), вхід із pull-up; GND — фізичний пін 6. Контакт між GPIO17 і GND дає LOW при замиканні. Відповідність LOW наявності мережі задається параметром. Обрив проводу може бути нерозрізненним із розімкненим контактом.

Для аналогового виходу можна розглянути ADS1115 через I²C: SDA GPIO2/пін 3, SCL GPIO3/пін 5, живлення 3.3 В/пін 1, GND/пін 6. Потрібні підтверджені діапазон, ізоляція, поріг і гістерезис. Входи АЦП також мають обмеження напруги. Підключення ще не затверджене. 220 В або 5 В безпосередньо до GPIO підключати не можна.

## Правила розеток

Параметри кожної розетки: `device_id`, назва, канал за потреби, режим `auto/manual`, дії `on/off/hold` та окремі `delay_minutes` для `mains_present` і `mains_absent`. Датчик має active level та debounce; аналоговий — поріг і гістерезис.

Погоджений сценарій: зникнення → OFF одразу; повернення → ON через 20 хвилин безперервної наявності. Спочатку достатньо двох правил для кожної розетки; багатокрокові сценарії додаються за потреби.

Реверс сигналу скасовує незавершений таймер. Розетки мають незалежні таймери. Перед командою та retry перевіряються сигнал, режим і покоління дії. Відправляється актуальний бажаний стан, а не історична черга. Після перезапуску датчик зчитується заново; реалізовано повний новий відлік затримки після старту.

Ручне керування переводить розетку в manual до повернення в auto. Ручний ON дозволений лише при підтвердженій наявності мережі. OFF-правило при зникненні діє також у manual; невідомий сигнал блокує ON і скасовує його таймер.

## eWeLink

Перевірено 2026-11-13 за [офіційною документацією](https://coolkit-technologies.github.io/eWeLink-API/#/en/OAuth2.0), на яку посилається https://dev.ewelink.cc.

- У `../.env` є `EWL_APPID`, `EWL_SECRET`; значення не копіюються в репозиторій.
- Потрібні OAuth облікового запису, зареєстрований redirect URL, access/refresh tokens та регіон авторизації. Регіон не визначається лише місцем Raspberry.
- OAuth code діє 30 секунд; обмін: `POST /v2/user/oauth/token`, refresh: `POST /v2/user/refresh`. Підпис HMAC-SHA256/Base64 формується за правилами конкретного запиту.
- Список: `GET /v2/device/thing`; стан і керування: `GET/POST /v2/device/thing/status`. Payload залежить від UIID: `switch` або канальні `switches`.
- Для Європи host `https://eu-apia.coolkit.cc`; інші регіони мають інші hosts. API acknowledgement не підтверджує фактичний стан.
- Документація вказує для free APPID 50 000 викликів/місяць/регіон і рекомендований інтервал ≥1 секунди. Поточна реалізація: batch HTTP-синхронізація кожні 120 секунд (≤10 пристроїв) і спільне обмеження частоти. WebSocket відкладено; інтерфейс показує час останнього спостереження. Фактичні дозволи APPID перевіряються при інтеграції.

## Вебінтерфейс

Адаптивна українська панель: наявність мережі, здоров'я датчика та eWeLink; картки обраних розеток із ON/OFF, online/offline/unknown, бажаним станом, режимом і відліком затримки. Кнопки керування, редагування правил, журнал подій. При втраті зв'язку показувати останній відомий стан із часом оновлення. Секрети не передавати браузеру.

Реалізовано Basic Auth у застосунку й custom-header токен для записів. Caddy отримує/поновлює Let’s Encrypt через відкриті 80/443; потрібні домен та email. DNS challenge для CGNAT потребує окремого модуля провайдера.

## Docker і відмови

Один контейнер, persistent volume для SQLite та захищеного сховища токенів, runtime environment/secrets, restart policy і healthcheck. GPIO — окремий Compose override з доступом лише до потрібного `/dev/gpiochip*` і відповідної групи. Без `privileged: true`. Перевірити ARM64-пакети та GPIO device на Raspberry. Симуляція працює без GPIO та хмарних секретів.

Для команди при зникненні мережі Raspberry, роутер/Wi-Fi та інтернет повинні залишатися доступними; розетка також має бути живлена. Резервне живлення залежить від схеми. Cloud API не гарантує вимкнення offline-розетки: відображати невиконану дію. Перевірити power-on state самої розетки після відновлення живлення.

## Уточнення до реалізації

1. Модель аналізатора, тип виходу, ізоляція та напруга; потрібне вимірювання струму чи наявності 220 В?
2. За потреби уточнити обрану політику: новий відлік після старту, блокування ON за невідомого сигналу.
3. Моделі/канали та ID розеток; правила для інших розеток.
4. Резервне живлення Raspberry, роутера і розеток; power-on state розеток.
5. Домен, email Let’s Encrypt, доступність 80/443, OAuth redirect URL; Basic Auth погоджено.

## Порядок реалізації

Спочатку — конфігурація, автоматизація з підставним годинником і mock-адаптери. Далі — OAuth, eWeLink, вебпанель і журнал; потім GPIO та Docker. Тести: debounce, реверс під час затримки, незалежні розетки, зміни правил/manual, restart, offline, timeout і refresh. Реальне керування перевіряється після погодження конкретної розетки та дії.
